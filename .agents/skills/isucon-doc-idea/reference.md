# ドキュメントの文言から施策を引く対応表

ISUCON5〜14 の当日マニュアル・アプリケーションマニュアル・レギュレーションを読み、講評・解説で「その文言に気づいたチームが何をしたか」を突き合わせてまとめたもの。資料の一覧は `sources.md` を参照。

出典の略記: `[12q]` = ISUCON12 予選、`[12f]` = ISUCON12 本選、`[13]` / `[14]` = 本選のみの回。「」内は原文から抜き出した文言。

---

## 0. 読み方の原則（過去問から得た教訓）

1. **当日マニュアル > アプリケーションマニュアル > レギュレーション の順に読む。** ISUCON9 以降のレギュレーションはほぼ定型文で、施策のヒントは当日マニュアルとアプリ仕様に集中している。両者が矛盾したら当日マニュアルが優先される（[10q] 以降は明記）。
2. **猶予や許容は「どのエンドポイントの、どの項目に、何秒」まで読み分ける。** [14] では「nearby-chairs の座標は過去3秒以内でよい」とあったが、猶予があるのは座標だけで、割り当て可能かどうかは即時に反映する必要があった。レスポンス全体を3秒キャッシュすると fail する。
3. **書かれていないことは自由、明示的に禁止されたことは不可。** [8f] の仕様は「bcrypt でハッシュ化」とだけ書き、コストには触れていなかったので、最小コストにできた。一方 [13] は「bcrypt のコストを変更してはいけません (MUST NOT)」と明記している。毎回、文言を確認すること。
4. **書いてあっても、今やるべきとは限らない。** 例: bot に 503 を返す [10q]（初期は bot がほとんど来ない）、Web Push [10f]（実装しても Thundering Herd でスコアが下がりがち）、SSE [14]（必須ではない）、Idempotency-Key [14]（ほぼブラフ）、使われていない /robots.txt [6q]（ボツ案の名残）。効果は負荷状況から判断する。
5. **加点されない API は「速くする対象」ではなく「遅くしてもよい・邪魔さえしなければよい対象」。** [7q] では加点ゼロの `GET /fetch` をわざと遅くしてメッセージをまとめ取りさせるのが正解だった。
6. **アプリ仕様の業務ルールは、キャッシュや事前計算をしてよい根拠になる。** 「終了後は変動しない」「受け取り済みは変更されない」「更新する機能がない」といった記述を探す。
7. **初期実装の不自然な部分もドキュメントの一部として読む。** 一見無駄な sleep [7q]、dropProbability [11q]、TODO コメント [8f]、503 を返す未実装 API [10f]、二重発券の既知バグ [9f] など。
8. **作問者自身が「ドキュメントから改善のヒントを得る用途での AI 活用は少なかった」と書いている [14]。** このスキルの存在意義の根拠になる。

## 1. 反映の猶予・遅延の許容 → キャッシュ・非同期化・バッチ化

| シグナルとなる文言 | 示唆 | 典型施策 | 事例・結果 |
|---|---|---|---|
| 「N秒以内に反映されればよい」「N秒の猶予が許容されます」 | N秒までは古いデータを返してよい／書き込みを後回しにしてよい | N秒以下の TTL キャッシュ、非同期ワーカー、キュー + 定期バルク INSERT | [8q]「1秒以内の遅延は許されます」/ [8f]「info に返すデータは原則1秒以内に反映」→ 講評「裏を返すと1秒間キャッシュしてもよい」。重い集計クエリはクエリを改善せずキャッシュで解決できた |
| 猶予の起点が **書き込み API** に紐づいている | 書き込みの時点で集計・確定値を作ってしまえばよい | 書き込み時（イベント時）に事前計算して保存。レスポンスは先に返し、保存は非同期 | [12q] finish → billing に3秒の猶予。講評「finish のときに請求額が確定するので、BillingReport をそこで生成してストレージに入れてね!」「3秒も猶予があるので、レスポンスは先に返して請求情報の保存は非同期に」 |
| 状態変更 API → 参照 API に N秒の猶予 | 参照 API の結果をキャッシュし、更新イベントで破棄 | レスポンスを丸ごとキャッシュし、更新時に purge | [12q] disqualified → player/ranking に3秒の猶予 → player API をキャッシュ |
| 「反映が遅れることをベンチマーカーは許容しています」 | 受け付けと反映を分離できる | 受信 API はすぐに 202 を返し、キュー経由で一定間隔ごとにバルク INSERT | [11q] `POST /api/condition` → 講評「キューに詰めて、複数リクエストを跨いでまとめたコンディションを一定間隔で INSERT」 |
| 外部サービスへの送信遅延の許容（「10秒までが許容」） | 外部 API 呼び出しを同期処理から外せる | 送信キュー + まとめ送信（bulk API があれば使う） | [8f] isulogger は10秒の遅延を許容 + `POST /send_bulk` → 使わなければ特別賞(15000点)に「絶対に届かない」 |
| 通知について「状態変更から3秒以内に通知」「マッチ後30秒の猶予」 | ポーリング間隔やバッチ処理の周期を広げる余地がある | `retry_after_ms` を調整、マッチング処理のバッチ化 | [14] 間隔を伸ばせば負荷は下がるが満足度も下がる → 序盤は間隔を延ばし、終盤に詰める |

**落とし穴**
- 猶予の境界がシビアなことがある。[10f] では1秒キャッシュを単純に実装すると、詰まったときに1秒を超えて fail した。singleflight、Varnish の grace、非同期更新で Thundering Herd を防ぐ。
- 猶予は項目単位（原則 2）。[11q] では condition と graph の間は1秒以内に整合させる必要があった。
- 反映を遅らせると加点の機会が減る場合がある。[11q] には「反映を遅らせた場合、加点の機会が減る可能性に留意」と書かれていた。

## 4. 不変性・更新タイミングが限られていることの記述 → 永続キャッシュ・事前計算・データ圧縮

| シグナル（アプリ仕様の業務ルール） | 示唆 | 施策 | 事例 |
|---|---|---|---|
| 「〇〇後は変動がない」「終了後は新たな入稿ができない」 | 確定した値は永続的にキャッシュしてよい | 確定時に一度だけ計算して保存 | [12q] 仕様書自身が「それ以降のランキングや課金額には変動がないので結果をキャッシュ可能になる」と明記 / [11f]「GPA は修了した科目のみが対象」→ 終了済み科目の総合点を永続キャッシュ、GPA 一覧を coalescing |
| 「終了するまでは課金に加算しない」 | 終了前は計算せず定数を返す | 早期 return | [12q]「finish を呼んでない大会は加算しない」→ 終了前は常に0 |
| 「CSV 上で最後に出現した行が採用」「最新の〇〇のみ表示」 | 最新以外の行は不要 | 初期データを含めて圧縮、UPSERT | [12q] player_score を最終行だけに圧縮 / [14] chair_locations は最新位置と総距離だけで足りる → UPSERT テーブル |
| 「時刻が重複することはない」「常に先の時刻となる」 | 自然キーを PK にでき、最新値をメモリで保持できる | 複合 PK、最新値キャッシュ | [11q] (jia_isu_uuid, timestamp) の複合 PK |
| 〇〇を変更・削除する機能が存在しない | そのテーブルは実質不変 | 全件をオンメモリに載せる | [5q] users を変更する機能がない／「友だちをやめる」機能がない → users と relations を全件キャッシュ |
| 「受け取り済みは〜」「確定済みは〜」 | 履歴部分は変更されない | 未処理分と履歴でテーブルを分割 | [12f] 受け取り済みプレゼントを履歴テーブルへ |
| マスタは `/initialize` 以降は更新されない／特定フェーズ後は更新されない | フェーズ単位でキャッシュできる | 起動時ロード、フェーズ終了時にキャッシュ化 | [10f] contest_config、登録フェーズ後の teams |

## 6. 減点・失格・打ち切り条件 → 何を絶対に壊してはいけないか

| シグナル | 示唆 | 施策 | 事例 |
|---|---|---|---|
| 「critical error」「1回で失格」の対象 API | 正しさが最優先。キャッシュや非同期化は慎重に | 排他制御、冪等性の確保 | [9q] 同一商品の二重決済は critical → 商品ごとの mutex / [9f] 二重発券 / [12q] 書き込み5系統は 10%/件 / [14] 想定外の通知・状態遷移 |
| タイムアウトが減点にならない・失格にならない | 応答を捨ててでも他を優先してよい | 早めに失敗させる、受け付けだけ行う | [11q] `POST /api/condition` は「一切の減点や fail は発生しません」/ [10q] CSV 入稿以外はタイムアウトで減点なし |
| 「タイムアウトや 500/503 エラーは無視」「加点も減点もしない」 | 高負荷時のエラーは許容される | デッドロックがまれに起きても速い実装を選べる | [7q] [8q] [10q] / [8q] 講評「デッドロックが低確率で発生するが高速な実装も選択できるように」 |
| 特定 API の失敗だけ即失格 | その API を最優先で安定させる | バルク INSERT、別リソースへの退避 | [10q] CSV 入稿の失敗やタイムアウトは critical → 負荷後半でのタイムアウトを防ぐためバルク INSERT |
| エラー率・エラー件数で打ち切り | エラーを出さないことが負荷量（＝スコア）の前提 | — | [5q] 5xx 1%・4xx 10% / [14] warning 200件で打ち切り |
| 減点率がスコアに比例する | エラー1件の重みがスコアに比例して大きくなる | — | [8f] score×(1−err/100) / [12q] (err×1 + critical×10)% |
| 明示された減点対象外 | そのログ・エラーは無視してよい | — | [9q] [9f] 終了時に切断された 499 は対象外 / [13] 特定の「一般エラー」は減点対象外 |
| 「既知の不具合」 | 初期実装のバグ。直すことが前提の場合もある | — | [9f]「初期実装ではロック機構がうまくなく、二重発券される場合がある」 |

## 7. タイムアウト値 → 処理時間の予算

| シグナル | 示唆 | 施策 | 事例 |
|---|---|---|---|
| POST に「N秒以内」+ 大きな減点 | 書き込み API の SLA を厳守する | 書き込み経路の重い処理を非同期化 | [5q] POST が3秒を超えると −100 / [6q] −200 |
| 極端に短いタイムアウト（100ms〜1秒） | その API に同期処理を置けない | すぐ返して後で処理 | [11q] condition は 100ms（減点なし）、その他は1秒 |
| 通知系の長いタイムアウト（60秒） | ロングポーリングが可能 | 状態変化まで待ってから返す | [14] notification は60秒 → 講評「ロングポーリングすることも一応想定していました」 |
| `/initialize` の制限時間 | 長ければ初期化時に事前計算ができる。短ければ重い処理は置けない | 事前計算結果の dump を流し込む | [6q] 5秒（短い）/ [12f] 60秒 / [13] 42秒 / [12q] 講評: billing_report を initialize 後に mysqldump して流し込む |
| 「負荷走行後 N秒待ってから整合性チェック」 | 非同期処理はN秒以内に収束すればよい | ジョブキューの上限遅延をN秒に設計 | [9f]「5秒以上待ってから整合性チェック…外部決済サービスのキャンセルなど整合性をとってください」→ キャンセルを5秒以内ごとにバルク処理 / [10f] 同様に5秒 / [14] 決済は終了後5秒以内に完了 |
| 負荷走行後にだけ実行される重い API | 負荷中ではなく事後に一回だけ動く | 走行中の性能より、メモリ・スワップ対策 | [8q] レポートは事後に60秒以内 → 講評「最後に一気に Swap が膨らむのが大きなヒント」→ ストリーミング出力 |

## スキルが文書から必ず抽出する項目（チェックリスト）

1. スコア計算式（加点対象の API と配点、倍率、加点されない API）
2. 減点・失格・打ち切り条件（critical の対象 API、減点にならないエラーやタイムアウト）
3. タイムアウト値（API ごと、`/initialize`、通知系）
4. 反映の猶予・キャッシュ許可（API ごと、項目ごと、秒数、起点となるイベント）
5. 「ベンチマーカーが検知しない限り」系の常設の許可の有無
6. 負荷調整弁（initialize の戻り値、403/429、retry_after、有効化フラグ、間引き率）
7. ベンチマーカーの挙動（負荷の上がり方、Conditional GET、圧縮、静的ファイルの取得有無、リダイレクト、DNS）
8. 拒否してよいトラフィック（bot、BAN、失格者、NXDOMAIN）
9. 外部サービスの制約（レート制限、bulk API、保証期間、冪等性キー、遅延）
10. 業務ルール上の不変性・更新タイミング（終了後不変、最新のみ採用、変更機能の不在、マスタ更新）
11. 自由に変えてよいと明示された部分（ID、内部 API、通知方式、ページング、誤差）
12. 禁止・制約（パスワード、メモリ、件数、順序、ヘッダ、冪等性、時刻）
13. 負荷走行後の整合性チェックまでの猶予（非同期処理の締め切り）
14. 追試条件（再起動手順、再現率、永続化チェック）
15. 環境（台数、スペック、帯域、ベンチマーカーの入口、初期構成）
16. 既知の不具合・FAQ・サポートの回答（ルールの補足や例外）
