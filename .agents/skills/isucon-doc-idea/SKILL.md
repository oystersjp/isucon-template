# ISUCON Doc Idea

## 目的

競技ドキュメントの文言から、スコアを上げる施策の機会と、施策を潰す制約を漏れなく抜き出す。根拠は過去回（ISUCON5〜14）で「その文言に気づいたチームが何をしたか」をまとめた `reference.md` に置く。

- やること: ドキュメントの取得、記述の抽出と原文引用、`reference.md` との照合、施策案と制約の提示。
- やらないこと: ユーザーの承認なしにコードを変更すること。ドキュメントに根拠のない推測を、ドキュメント由来として断定すること。

## ワークフロー

### 1. 入力ドキュメントをリポジトリ内から探す

最初にリポジトリ（`git rev-parse --show-toplevel`）の中を探す。ユーザーに URL を聞くのはその後。

```bash
ROOT=$(git rev-parse --show-toplevel)
# ファイル名で探す
find "$ROOT" \( -name node_modules -o -name vendor -o -name .git -o -name .agents -o -name target \) -prune -o -type f \
  \( -iname '*manual*' -o -iname '*regulation*' -o -iname '*spec*.md' -o -iname '*cautionary*' \
     -o -iname 'openapi*.y*ml' -o -iname '*.md' -path '*/docs/*' \) -print
# 本文のキーワードで探す（ファイル名が手がかりにならない場合）
grep -rlE --include='*.md' --include='*.txt' --include='*.html' \
  --exclude-dir={node_modules,vendor,.git,.agents,target} \
  '当日マニュアル|アプリケーションマニュアル|レギュレーション|負荷走行|スコア計算|ベンチマーカー' "$ROOT"
```

本文が無くても、**文書へのリンク** がリポジトリ内にあればそれを使う。

```bash
# README などに書かれた当日マニュアル等へのリンク（gist / GitHub / hackmd / isucon.net）
grep -rnoE --include='*.md' --exclude-dir={node_modules,vendor,.git,.agents,target} \
  '\[[^]]*(マニュアル|レギュレーション|仕様)[^]]*\]\([^)]+\)' "$ROOT"
# チームの ISSUE テンプレート（.github/ISSUE_TEMPLATE/isucon.md）から作った当日用 issue に
# 「レギュレーション / 当日マニュアル / アプリケーションマニュアル」のリンク欄がある
gh issue list --state all --limit 20 --json number,title,body \
  -q '.[] | select(.body | test("当日マニュアル")) | "#\(.number) \(.title)\n\(.body)"'
```

テンプレートそのものの空リンク `[当日マニュアル]()` は対象外とする。URL が入っているリンクだけを使う。

見つかった候補は中身を確認し、次の3種類に分類する。README・CHANGELOG・ライブラリの文書など、競技と関係ないものは除く。

| 種類 | 重要度 | 見分け方 |
|---|---|---|
| 当日マニュアル | 必須 | スコア計算、負荷走行、タイムアウト、追試、禁止事項の節がある |
| アプリケーションマニュアル / 仕様書 / openapi.yaml | 強く推奨 | 用語、業務ルール、エンドポイント仕様、外部サービス API がある |
| レギュレーション | 任意 | 参加資格、ソフトウェア事項、禁止事項。ほぼ毎回同じ定型文なので、定型との差分だけ見ればよい |

### 2. 見つからない・足りない場合はユーザーに求める

当日マニュアルの本文もリンクもリポジトリや issue に無い場合は、作業を止めてユーザーに URL か本文を求める。アプリケーションマニュアルが無い場合も、当日マニュアル内にリンクがあればそれを取得し、無ければ同様に求める。推測で補って進めない。

依頼文の例:

> リポジトリ内に当日マニュアルが見つかりませんでした。URL（gist / GitHub / hackmd など）を教えてください。ポータルなどログインが必要なページの場合は、本文をそのまま貼り付けてください。見つかったもの: (見つかったファイルの一覧。無ければ「なし」)

受け取った URL は次の方法で取得する。

| URL | 取得方法 |
|---|---|
| `gist.github.com/<user>/<id>` | `gh api gists/<id> -q '.files[].content'` |
| `github.com/.../blob/...` | `gh api repos/<owner>/<repo>/contents/<path>?ref=<ref> -H 'Accept: application/vnd.github.raw'` |
| `hackmd.io/<id>` | `curl -sL https://hackmd.io/<id>/download`（Markdown が取れる） |
| `isucon.net/archives/<id>.html` | WebFetch、または curl で取得し本文（article-body）を抽出 |
| その他 / ログインが必要なページ | 本文の貼り付けを依頼する |

取得した文書は、次回以降もリポジトリ内で見つかるよう `docs/contest/` に Markdown で保存し、保存先をユーザーに伝える。文書中のリンクの先（アプリケーションマニュアル、FAQ、外部 API 仕様）も同じ手順でたどる。

### 3. 文書から記述を抽出する

`reference.md` 末尾の「スキルが文書から必ず抽出する項目」の16項目について、該当箇所を **原文のまま引用** し、出典（ファイル名と見出し）を添える。該当が無い項目は「記載なし」とする。記載が無いこと自体が「自由にしてよい」という意味を持つ場合がある（`reference.md` の 0-3 を参照）。

抽出で特に注意すること:

- 猶予やキャッシュ許可は、**エンドポイント・項目・秒数・起点となるイベント** の単位で分解する。レスポンス全体に適用してよいかどうかは区別する（ISUCON14 の座標3秒の例）。
- スコア計算から、加点対象・配点の比・**加点されない API** を表にする。
- 失格・critical の対象 API は、施策のリスク評価に使う。
- `/initialize` のレスポンスで返す値、403/429/503 を返してよい条件、ポーリング間隔など、**負荷を調整できる仕組み** は漏らさない。
- 初期実装に関する記述（既知の不具合、sleep、間引き、TODO、503 を返す未実装 API）も拾う。

### 4. reference.md と照合して施策化する

抽出した記述を `reference.md` の観点 1〜15 と照合し、似た過去事例を根拠として施策案に落とす。過去事例と違う点（秒数、対象項目、禁止事項）があれば明記する。`reference.md` の原則 4 に従い、「書いてある＝やるべき」とせず、負荷の段階と効果で優先度を付ける。

### 5. （任意）実装の該当箇所を特定する

リポジトリにアプリのコードがある場合は、施策の対象エンドポイントのハンドラ・クエリをルーティング定義から grep して `file:line` で示す。計測結果（alp / pprof / slow log）があれば優先度付けに使う。コード全体の改善案は `isucon-tuning-idea` スキルの担当なので、ここではドキュメント由来の施策に関係する箇所に絞る。

## 出力フォーマット

1. **入力文書**: 使用した文書（パスまたは URL と種類）。取得できなかった文書があればそれも書く。
2. **抽出サマリ**: 16項目の表（項目 / 原文引用 / 出典）。
3. **施策アイデア**（優先度順）。各項目に次を書く:
   - 根拠となる原文（引用）
   - 解釈（何をしてよい／何が効くか）
   - 施策（具体策。対象エンドポイントやコード箇所が分かれば添える）
   - 参考となる過去事例（`reference.md` の回と観点）
   - 期待効果（大・中・小）とリスク（失格・減点条件との関係）
   - 着手タイミング（序盤 / 負荷が上がってから / 終盤の調整）
4. **壊してはいけない制約**: 禁止事項、critical 条件、即時反映が必要な項目、追試条件の一覧。
5. **要確認事項**: 文言が曖昧で、ポータルで運営に質問すべき点。
6. **推奨する次の一手**: 最初に着手すべき1〜3件。

## 参照ファイル

- `reference.md`: 観点別の「文言 → 示唆 → 施策 → 事例」対応表と、抽出チェックリスト。
- `sources.md`: ISUCON5〜14 の各ドキュメントの URL。過去問の練習時の入力や、事例の原文確認に使う。
