# isubench

問題ごとに違うのは `mybin/isubench/isubench.env` だけ。ツールは特定の問題に依存しない。

## 準備 (競技開始後に1回、10分ほど)

1. `make isubench/guess` を実行し、出た候補で `mybin/isubench/isubench.env` を埋める。
   - `ISUBENCH_NGINX_CONF` と `ISUBENCH_UPSTREAM` には、アプリへ転送している `proxy_pass` (または `upstream` の `server`) のファイルと転送先を書く。例は `localhost:8080`。この文字列はファイル内で全部、録画用の中継に置き換わる。別の用途で同じ文字列が出てくるなら、もっと長い文字列にする。
   - `ISUBENCH_TARGET` は、nginx が 443 で待ち受けているなら `https://127.0.0.1`、80 なら `http://127.0.0.1` にする。
   - `ISUBENCH_SERVICES` には、アプリ・DB・nginx と、裏で動く常駐プロセスの systemd 名を書く。
2. アプリのコードで、外部サービスを HTTP で呼んでいる箇所を探す (`http.Post`, `NewRequest`, `initialize` で受け取る URL など)。あれば `ISUBENCH_STUB` にスタブのアドレスを書く。スタブは POST には 204 を、GET には `[]` を返す。それ以外の応答が要るサービスは、スタブでは代わりにならない。
3. `make isubench/record-start` を実行し、ポータルから公式ベンチを1回回し、`make isubench/record-stop` を実行する。
   - 録画中は nginx の向き先が中継になる。止め忘れても、600秒で自動的に戻る。
   - `record-stop` は initialize の本文を表示する。公式ベンチ側の URL (例 `http://192.168.0.10:12345`) があれば、`ISUBENCH_REWRITE=old=new` でスタブに向ける。
4. 正常版のまま `make isubench/baseline` を実行する。
   - `警告: 正常版なのに ... のステータスが録画と違う` が出たら、再生が成立していない。`~/isubench/diff.txt` を見る。401/403 が多いならトークンの形が既定 (英数字・`_`・`-` が20文字以上) に合っていないので、`ISUBENCH_ID_REGEX` を書く。404 が多いなら ID の付け替えに失敗しているか、初期化のパスが既定 (`/initialize` か `/api/initialize`) と違うので、`ISUBENCH_BARRIER` を書く。外部サービスのエラーなら手順2に戻る。

## 変更ごとの判定

1. 変更をデプロイして `make isubench/check` (20秒) を実行する。録画の先頭20秒を等速で流す。
2. `== 正しさ` を読む。
   - `NG` なら、どのエンドポイントの何 (status, body, 5xx, err) が、正常版の最大何件に対して何件になったかが出ている。`~/isubench/diff.txt` で食い違いの例を見る。
   - 食い違いがバグなら直す。公式ベンチには流さない。
   - 速くするために見え方が変わった (キャッシュで少し古い値を返す、非同期で反映が遅れる) だけなら、それが仕様で許されるかを競技マニュアルで確かめてから進める。
3. `== 負荷` を読む。
   - CPU 秒が `軽くなった` か、平均レスポンスが `速くなった` なら、良い変更の候補にする。
   - 両方とも `差なし` でも、効いていないとは限らない。公式ベンチの後半の負荷でしか効かない改善がある。性能を確かめたいときは `make isubench/check-full` を使う。録画を全部流すので、公式ベンチ1回分の時間がかかる。基準は `make isubench/baseline-full` で別に作る。
4. 採用した変更をデプロイしたら、`make isubench/baseline` で基準をその版に更新する。比べる相手は常に「今の正常版」にする。
5. 採用した変更がいくつかたまったら、公式ベンチを回して点数を確かめる。スコアが大きく伸びたら録画を撮り直す (手順3と4)。

## 判定の根拠と限界

ISUCON14 (c5.large、2コア) で10バージョンと3種類のバグを測った値。別の問題では揺れ方が違うかもしれない。

- 同じ版を繰り返し測ると、等速の CPU 秒は 0.4〜2%、平均レスポンス時間は最大40%揺れた。そのため判定の幅は CPU 秒が5%、レスポンス時間が25%にしてある。
- `check` (先頭20秒) は、スコア +69% の変更をレスポンス時間 -52% で検出した。一方、スコア +68% の別の変更は検出できなかった。公式ベンチは時間とともに負荷を上げるので、先頭は軽い。`check-full` では両方を検出した (レスポンス時間 -49% と -65%)。
- 再生は録画時の速さで送り続けるので、アプリが追いつかないと負荷が積み上がる。ISUCON14 で重い録画を2倍速以上で流すと、どの版でも飽和して、CPU 秒が9〜44%揺れた。`警告: 予定 N 秒の再生に M 秒かかった` が出たら、その結果は使わず `ISUBENCH_SPEED` を 1 に戻す。
- 料金計算のバグは、公式ベンチと同じく検出できた。並び順や距離計算のバグは、公式ベンチの負荷走行も `check` も見逃した。乱数やタイミングで、正常版でも半分以上食い違うエンドポイントでは、小さなバグは埋もれる。
- 数値 ID は、`id`・`xxx_id`・`xxxId` のキーと、パスの数字だけの区切りを付け替える。それ以外の場所 (例 `?page=3` の値を ID として使う) は付け替えない。
- SSE (`text/event-stream`) のレスポンス本文は録画しない。
- 録画中に nginx が複数台のアプリへ振り分ける構成だと、中継の先の1台にしか届かない。録画は1台構成のうちに撮る。
- 再生は自分のサーバーにだけ送る。ポータルや他チームには送らない。
